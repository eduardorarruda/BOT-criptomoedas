# Contrato entre os serviços

Fonte da verdade dos formatos: `packages/contratos` (esquemas Zod). As respostas da API REST estão em [`api.ts`](../packages/contratos/src/api.ts) e [`backtest.ts`](../packages/contratos/src/backtest.ts); os corpos dos webhooks, em [`webhook-esquemas.ts`](../packages/contratos/src/webhook-esquemas.ts). A tela importa `@zentrade/contratos/esquemas`, subcaminho sem código de servidor (sem `node:crypto`). Este documento fixa **quem fala com quem, por onde**. Decimais trafegam sempre como texto (`"0.00123"`); horários em milissegundos UTC.

## Serviços e portas (desenvolvimento)

## Fluxos internos

- **Motor → banco:** grava decisões, ordens, execuções e candles pelas portas de `@zentrade/contratos` (`PortaDecisoes`, `PortaOrdens`, `PortaRobos`), implementadas em `packages/banco`.
- **Motor → Redis:** publica `Evento` (JSON) em `zentrade:eventos`. A API retransmite pelo WebSocket.
- **Motor → Redis (batida):** grava em `zentrade:motor:batida` o instante (ms) em que esteve vivo pela última vez. A API considera o motor vivo se a batida tem até 120 s (`/saude` e o webhook do vigia).
- **Motor → agente:** `POST http://agente:8081/analisar`, cabeçalho `Authorization: Bearer $AGENTE_SEGREDO`, corpo `PedidoAnalise` serializado (decimais em texto; `analiseId` opcional), resposta `{ proposta: PropostaAgente, custoUsd: "0.0123" }`. Timeout 60 s; falha = não operar. O provedor (API ou Claude Code), o modelo e a conta vêm da configuração da dona do robô.
- **Agente → Redis:** com `analiseId` no pedido, cada ferramenta consultada vira um `EventoAnalise` (`etapa: { ferramenta, descricao, em }`, `concluida: false`) em `zentrade:eventos`. A conclusão (com `decisaoId`) é do motor.
- **API → motor (backtest):** job na fila BullMQ `backtests` com `{ backtestId }` (o `jobId` é o próprio id: reenviar não duplica); o motor lê o pedido no banco e grava o resultado lá, com as métricas de `MetricasBacktestEsquema` (`resultadoLiquido`, `maiorQueda`, `maiorQuedaPercentual`, `operacoes`, `acertos`, `taxaAcerto`, `taxasPagas`; opcionais `patrimonioFinal`, `ordens`) e a curva `[{ em, patrimonio }]`. Métrica fora do contrato não sai pela API: o backtest aparece com `metricas: null` e um `erro` explicando.
- **API → n8n:** `POST $N8N_URL/webhook/zentrade-proposta` (corpo `PropostaCriada`) e `POST $N8N_URL/webhook/zentrade-alerta` (`{ tipo, titulo, mensagem, em }`), ambos assinados. O n8n responde **202** quando aceita, **401** com assinatura errada ou vencida e **400** com corpo fora do contrato.
- **n8n → API:** webhooks assinados em `/webhooks/n8n/*`.

### Assinatura dos webhooks (os dois sentidos)

Cabeçalho `X-ZenTrade-Assinatura: t=<segundos>,v1=<hmac-sha256-hex de "t.corpo">`, segredo `N8N_WEBHOOK_SEGREDO` (≥ 32 caracteres), validade 5 min. Implementação: `assinar` / `verificar` em `@zentrade/contratos`.

- A assinatura é sobre o **corpo bruto**, byte a byte, exatamente como sai no fio. Quem assina precisa mandar a mesma string que assinou (no n8n: corpo `raw`, `application/json`); reformatar o JSON depois de assinar invalida a assinatura.
- **Corpo vazio assina a string vazia** (`"t."`): é o caso de `POST /webhooks/n8n/saude`.
- **Uso único (anti-replay):** a API guarda cada assinatura aceita no Redis (`zentrade:webhook:assinatura:<caminho>:<v1>`, `SET NX EX`) pelo tempo em que ela ainda vale (até o carimbo + 5 min). A mesma requisição de novo recebe **409** `webhook_repetido`; para reenviar, assine de novo. Sem Redis, o webhook é recusado com **503** `anti_replay_indisponivel` (falha fechada).

## API REST (`/api/v1`)

**Autenticação.** Sessão em cookie `httpOnly` + `SameSite=Strict` (tela) ou `Authorization: Bearer <token>` (CLI, MCP, n8n). Tokens têm escopo `leitura` ou `operar`.

**CSRF.** `POST /sessao` e `GET /sessao` devolvem `{ usuario, csrf }`. Toda escrita com sessão (`POST`, `PATCH`, `DELETE`) leva o cabeçalho `x-csrf-token` com esse valor (também está no cookie legível `zt_csrf`). Sem ele: **403** `csrf_invalido`. Tokens Bearer não usam CSRF.

**Reautenticação.** Ações críticas (desligar a parada total, cadastrar chave de corretora, criar token, gerar o segredo do 2FA, ligar dinheiro real) exigem senha ou código 2FA confirmados nos últimos 5 minutos (`POST /sessao/confirmar`); o login conta como confirmação. Sem isso: **403** `reautenticacao_necessaria`. Ações críticas não aceitam token.

**Erros.** Sempre `{ "erro": { "codigo": "texto_curto", "mensagem": "frase para a pessoa" } }` (`ErroRespostaEsquema`). Códigos que quem chama costuma tratar: `nao_autenticado` (401), `codigo2fa_necessario` (401, o login pede o código do app), `reautenticacao_necessaria` (403), `csrf_invalido` (403), `escopo_insuficiente` / `exige_sessao` (403), `dados_invalidos` (400), `nao_encontrado` (404), `muitas_tentativas` (429).

**Prazo de aprovação.** Uma decisão em `aguardando_aprovacao` (modo Sugerir) vale `APROVACAO_VALIDADE_MIN` minutos (padrão 15); depois disso aprovar ou recusar devolve **409** e a decisão expira.

Detalhes que valem para várias rotas:

- **Escopo dos tokens:** leituras (`GET`) aceitam `leitura`; escritas que operam (robôs, decisões, estratégias, parada total, backtests, notas) exigem `operar`. Contas, tokens e 2FA só pela tela, com sessão.
- **`/automacoes`:** a API não consulta o n8n. O status vem do que ela viu: webhooks assinados recebidos (`zentrade-vigia-saude` → `/webhooks/n8n/saude`, `zentrade-noticias` → `/conhecimento`, `zentrade-aprovacao` → `/aprovacao`) e avisos que ela enviou (`zentrade-aprovacao`, `zentrade-alertas`). Guardado no Redis em `zentrade:automacoes`. Fluxo agendado sem sinal há mais de 3 intervalos aparece com `ativa: false`. Relatório diário e revalidação semanal usam a API com token e não aparecem.
- **Assistente:** a API autentica (sessão) e repassa ao agente em `POST $AGENTE_URL/assistente/responder` (Bearer `AGENTE_SEGREDO`, corpo `PedidoRespostaAgente` com o `usuarioId` da sessão), que responde em NDJSON (`EventoRespostaAgente` por linha). O agente lê a configuração da pessoa (`assistente_config`) e os dados dela sob RLS; as ferramentas são só de leitura. `GET $AGENTE_URL/assistente/estado` diz os provedores, as contas do Claude Code e os modelos sugeridos.
- **`/tempo-real`:** com sessão, só aceita a origem `ZENTRADE_ORIGEM_WEB`. A cada 30 s a API confere se a sessão ainda vale (ou se o token não foi revogado); se não, fecha a conexão com o código **4401**. Se não der para conferir (banco fora), fecha com **1011**.

### Ao vivo (`/aovivo`)

Para a tela "Ao vivo" abrir já preenchida, a API guarda os últimos eventos de cada robô que passaram pelo canal `zentrade:eventos`. O WebSocket `/tempo-real` continua sendo o fluxo ao vivo; estas rotas só contam o que aconteceu há pouco.

| Método e caminho               | Consulta                        | Resposta                                                                                                          |
| ------------------------------ | ------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `GET /aovivo/:roboId/recentes` | `?limite` (1 a 400, padrão 400) | `{ eventos: [{ recebidoEm, evento }] }` do mais antigo ao mais novo; robô de outra pessoa ou inexistente: **404** |
| `GET /aovivo/recentes`         | `?limite` (1 a 400, padrão 400) | o mesmo, juntando todos os robôs da pessoa, ordenado por `recebidoEm`                                             |

- **Quais eventos:** `candle`, `sinal`, `analise`, `decisao`, `risco`, `ordem` e `posicao`. `preco` e `saude` não são de um robô e não entram (a tela recebe os preços pelo WebSocket). `evento` segue `EventoEsquema`; `recebidoEm` é a hora (ms) em que a API recebeu.
- **Guardado no Redis:** lista `zentrade:aovivo:robo:<roboId>` (mais novo primeiro), com teto de 400 e validade de 24 h renovada a cada evento. A ordem só diz a decisão: o robô vem do evento da decisão (lembrado em `zentrade:aovivo:decisao:<decisaoId>`, 24 h) ou, se a API não o viu, do banco. Gravação em fila, na ordem de chegada.
- **É memória curta, não fonte da verdade:** sem Redis, o evento não entra no histórico (fica no log) e as rotas respondem 500; decisões, ordens e posição continuam no banco e nas rotas de sempre. Escopo `leitura`.

## Renda fixa e Pluggy (`/api/v1/renda-fixa`, `/api/v1/pluggy`)

Esquemas em [`renda-fixa.ts`](../packages/contratos/src/renda-fixa.ts); contas puras em [`packages/financas`](../packages/financas/src). Dinheiro e taxas em texto decimal; **taxas em %** (`"110"` = 110% do CDI, `"6.5"` = 6,5% ao ano); datas de calendário `AAAA-MM-DD`; "hoje" é o dia em São Paulo. Tudo isolado por pessoa (RLS). A API mostra fatos e contas: nada é recomendação.

Como as contas funcionam:

- **Posição.** Com valores da instituição (Pluggy: `amount` = bruto, `balance` = líquido, `taxes` = IR, `taxes2` = IOF), eles mandam (`fonte: "instituicao"`). Sem eles, o bruto sai dos índices: CDI e Selic dia a dia (fator de cada dia truncado em 16 casas), prefixado e taxa real em `(1 + taxa)^(du/252)`, IPCA mensal com pro rata por dias corridos (mês ainda não publicado entra pelo acumulado de 12 meses, avisado), poupança só nos aniversários. Dias úteis pelo calendário da ANBIMA. Tesouro é levado na curva (o preço de mercado pode ser outro; avisado).
- **Sem dado, sem conta.** Buraco na série vira `posicao: { disponivel: false, motivo }` com os dias que faltam; só o fim do período (a taxa de hoje, ainda não publicada) pode ficar de fora, e a posição diz até que dia foi.
- **Impostos.** IR regressivo (Lei 11.033/2004, art. 1º), IOF regressivo nos primeiros 30 dias (Decreto 6.306/2007), isenções de pessoa física (LCI, LCA, CRI, CRA, debêntures incentivadas, poupança). A MP 1.303/2025 perdeu a vigência em 08/10/2025 (Ato Declaratório CN nº 67/2025); conferido em 11/10/2026.
- **Índices.** Séries do SGS do Banco Central guardadas em `indicadores` (CDI 12, Selic 11, meta Selic 432, IPCA 433, poupança 195, TR 226). A API atualiza ao subir e a cada 6 h (só a cauda, com 10 dias de folga); a falha de uma série fica registrada nela.
- **Pluggy.** Sincroniza ao conectar, sob demanda e a cada 6 h. Só entra renda fixa (`FIXED_INCOME`) com indexador CDI, Selic, IPCA ou prefixado; o resto conta em `ignorados`. As caixinhas do Nubank chegam como CDBs da Nu Financeira (um por depósito, sem nome) e viram lotes do mesmo `grupo`. Título que some só é encerrado quando o item terminou de atualizar (`UPDATED`). No MeuPluggy só dá para conectar bancos nos 15 dias de teste da conta de desenvolvedor; por isso a API nunca apaga itens lá.

### Imobiliário (`/imobiliario`)

Investimentos imobiliários de cada pessoa (isolados por RLS) e simuladores. Esquemas em [`imobiliario.ts`](../packages/contratos/src/imobiliario.ts); contas em `@zentrade/financas`. Dinheiro em texto decimal (arredondado aos centavos nas respostas), taxas e percentuais em fração (`0.1` = 10%), datas de calendário em `AAAA-MM-DD`. CRI e LCI ficam na renda fixa. **Nada aqui é recomendação:** as respostas trazem `premissas`, e simulação vale o que valem as premissas.

| Método e caminho                                                   | Corpo / consulta                                                                | Resposta                                                                                                         |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `GET /imobiliario`                                                 | `?dataBase&cdiAnual`                                                            | `VisaoImobiliario`: patrimônio, investido, renda mensal (média líquida de 12 meses), alocação por tipo e `itens` |
| `GET /imobiliario/investimentos`                                   | `?dataBase&cdiAnual`                                                            | `ItemImobiliario[]` (`{ investimento, metricas, erroMetricas }`)                                                 |
| `POST /imobiliario/investimentos`                                  | `NovoInvestimentoImobiliario` (com `financiamento?` e `lancamentosIniciais?`)   | **201** `DetalheImobiliario` (escopo `operar`)                                                                   |
| `GET /imobiliario/investimentos/:id`                               | `?dataBase&cdiAnual`                                                            | `DetalheImobiliario`: investimento, métricas, lançamentos, tabela de amortização (com vencimentos) e cotação     |
| `PATCH /imobiliario/investimentos/:id` · `DELETE`                  | campos do cadastro (`null` limpa; tipo e moeda não mudam)                       | `DetalheImobiliario` · 204                                                                                       |

| `POST /imobiliario/simulacoes/financiamento`                       | `{ valorFinanciado, taxaAnual, prazoMeses, seguro…?, custosIniciais? }`         | `{ sac, price }`: tabelas completas, totais e CET aproximado (`cetMensal`, `cetAnual`)                           |

| `POST /imobiliario/simulacoes/rentabilidade`                       | `PedidoRentabilidade`                                                           | cap rate, yields, cash-on-cash, fluxos anuais, TIR, VPL, payback simples e descontado, premissas                 |
| `POST /imobiliario/simulacoes/fii`                                 | `{ cotas, precoCota, rendimentoMensalPorCota, meses, reinvestir?, rendaAlvo? }` | renda mensal, DY, evolução mês a mês e cotas para a renda alvo                                                   |
| `POST /imobiliario/simulacoes/ganho-capital`                       | `PedidoGanhoCapital`                                                            | ganho, reduções (FR1/FR2, Lei 7.713), isenções declaradas, imposto por faixa, alíquota efetiva e premissas       |

- **Tipos:** `aluguel`, `temporada` (exige `diaria` e `ocupacao`), `flip`, `terreno`, `planta`, `fii` (exige `ticker`), `reit` (exige `ticker` e `moeda: "USD"`; cada lançamento leva o `cambio` do dia), `crowdfunding` e `consorcio` (exige `valorCarta`, `prazoMeses` e `taxaAdministracao`). Financiamento só em imóvel físico.
- **Lançamentos:** `aporte` (dinheiro posto: compra, ITBI, reforma, parcela e lance de consórcio, compra de cotas com `quantidade`), `receita` (aluguel, diária, provento, juros), `despesa`, `resgate` (venda — categoria `venda` encerra um imóvel —, venda de cotas com `quantidade`, devolução de capital) e `imposto`. Valor sempre positivo, na moeda do investimento.
- **Métricas:** `investido`, `rendaAcumulada`, `despesas`, `impostos`, `resgatado`, `parcelasPagas`, `valorAtual` e `fonteValorAtual` (`cotacao` › `manual` › `valorizacao` › `custo`, ou `vendido`), `dividaAtual`, `patrimonioLiquido`, `resultadoBruto` (patrimônio + resgates + renda − aportes − parcelas), `resultadoLiquido` (bruto − despesas − impostos), `tirAnual` (TIR realizada pelas datas, como o XIRR), renda dos últimos 12 meses e, com `cdiAnual`, a comparação `cdi: { valorEquivalente, diferenca }` (o mesmo dinheiro, nas mesmas datas, rendendo o CDI informado, sem IR). Parcelas de financiamento com vencimento até a data-base contam como pagas.
- **Conferência:** toda escrita refaz as contas dentro da transação; venda de mais cotas do que a carteira tinha, ou REIT sem câmbio, dá **400** e nada é gravado.
- **Cotações:** opcionais, pela [brapi.dev](https://brapi.dev/docs) (`GET /api/quote/{ticker}`, token no cabeçalho `Authorization: Bearer`, um ticker por pedido, cache de 30 min; erro fica 5 min em cache). Sem `BRAPI_TOKEN`, `configurado: false` e vale o preço informado à mão (`valorAtual` = preço por cota).
- **Ganho de capital:** tabela progressiva da pessoa física (15% até R$ 5 mi; 17,5% até R$ 10 mi; 20% até R$ 30 mi; 22,5% acima — Lei 8.981/1995, art. 21, redação da Lei 13.259/2016), datada e configurável em `TABELA_GANHO_CAPITAL_PF` (conferida na Receita Federal em 11/10/2026). Isenções (único imóvel até R$ 440 mil, reinvestimento em 180 dias, pequeno valor até R$ 35 mil, compra até 1969) entram como declarações da pessoa; o cálculo oficial é o do GCAP.

### Patrimônio consolidado (`/patrimonio/consolidado`)

Tudo o que a pessoa tem, somado em reais: carteira cripto, renda fixa e imobiliário. Esquema em [`patrimonio.ts`](../packages/contratos/src/patrimonio.ts); a soma em `consolidarPatrimonio` (`@zentrade/financas`). Fica em `/patrimonio/consolidado` porque `GET /patrimonio` já é a curva do resultado realizado dos robôs. **Só informa:** cada classe vem das mesmas funções das rotas dela (`GET /carteira`, `GET /renda-fixa/resumo`, `GET /imobiliario`), nada é recalculado nem estimado aqui.

| Método e caminho              | Corpo / consulta | Resposta                                                                                                                                                                                         |
| ----------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /patrimonio/consolidado` | —                | `Patrimonio`: `{ moeda: "BRL", total, parcial, calculadoEm, cambio, classes[], avisos }`; cada classe `{ classe, situacao, valor, investido, fracao, itens, atualizadoEm, moedaOrigem, avisos }` |

- **Classes**, sempre nesta ordem: `cripto` (a conta **real** da Binance inteira, com USDT e saldo sem custo; testnet não entra), `renda_fixa` (valor bruto, antes de IR e IOF, como no extrato; `investido` = aplicado) e `imobiliario` (patrimônio líquido: valor atual − dívida; `investido` como na visão do imobiliário).
- **`situacao`:** `vazia` (nada cadastrado; não pesa), `completa`, `parcial` (entra com o que tem valor; o aviso diz o que ficou de fora) e `indisponivel` (sem valor em reais agora; `valor: null`, fora do total). `parcial: true` no topo quando alguma classe é parcial ou indisponível.
- **Cripto em reais:** o valor da conta em USDT × o último preço do par `USDTBRL` da Binance, lido da mesma tabela de preços da carteira (cache de 10 s, sem peso extra). O par vai em `cambio` (`{ par, preco, em, fonte: "binance" }`). Sem o par (ou com a Binance fora), a cripto aparece só em `moedaOrigem` (USDT) e fica fora do total; nenhuma taxa é inventada. `investido` da cripto é sempre `null`: o custo está em USDT e o câmbio de cada compra não é registrado.
- **`fracao`:** fatia da composição (6 casas), só das classes somadas e com valor positivo; `null` fora da soma ou com total zero. Dinheiro aos centavos.
- **`atualizadoEm`:** cripto, quando os preços foram lidos; renda fixa, a última conferência dos índices do Banco Central; imobiliário, a última alteração de cadastro.
- **Falhas:** a Binance fora não derruba a resposta (a cripto vira `indisponivel` com o motivo); erro de banco segue como nas outras rotas. Escopo `leitura`.

## Webhooks (`/webhooks/n8n`, assinados, sem sessão)

| Caminho                           | Corpo                                         | Efeito                                                         |
| --------------------------------- | --------------------------------------------- | -------------------------------------------------------------- |
| `POST /webhooks/n8n/aprovacao`    | `{ decisaoId, aprovada, porQuem }`            | aprova ou recusa a decisão (se ainda valer)                    |
| `POST /webhooks/n8n/conhecimento` | `{ fonte, titulo, url?, publicadoEm, texto }` | ingere no RAG (201 novo, 200 repetido)                         |
| `POST /webhooks/n8n/saude`        | —                                             | `{ motorVivoHaSegundos, robosPausados }` para o vigia de saúde |

Respostas comuns: **401** `assinatura_invalida` (ausente, errada ou vencida), **409** `webhook_repetido` (replay), **400** `json_invalido` ou `dados_invalidos`. O `url` do conhecimento só aceita `http://` ou `https://`.

**Dona do conhecimento.** O que chega por `/conhecimento` vai para `N8N_USUARIO_ID`. Com uma pessoa cadastrada, a variável pode ficar vazia (vai para ela). Com **mais de uma**, ela é obrigatória: sem ela, **409** `n8n_usuario_obrigatorio`; com um id que não existe, **409** `n8n_usuario_inexistente`.

## Esquema do RAG (tabelas em `packages/banco`)

```sql
documentos(id uuid pk, usuario_id uuid not null, fonte text check (fonte in ('diario','noticia','regra_corretora','estrategia','nota')),
           titulo text not null, url text, publicado_em timestamptz not null, hash_conteudo text not null,
           criado_em timestamptz not null default now(), unique (usuario_id, hash_conteudo))
trechos(id uuid pk, documento_id uuid not null references documentos on delete cascade, usuario_id uuid not null,
        ordem int not null, texto text not null, embedding vector(1024) not null,
        busca tsvector generated always as (to_tsvector('simple', texto)) stored, criado_em timestamptz not null default now())
-- índices: hnsw (embedding vector_cosine_ops), gin (busca), (usuario_id, documento_id)
```

Embeddings com 1024 dimensões (Voyage e o modelo local `bge-m3` produzem 1024). A ingestão é a mesma para a API e o agente (`ingerir` de `@zentrade/conhecimento`: normaliza, deduplica pelo hash do texto normalizado, divide em trechos e gera os embeddings), configurada por `EMBEDDINGS_PROVEDOR` (`voyage` ou `ollama`), `VOYAGE_API_KEY`, `VOYAGE_MODELO`, `OLLAMA_URL` e `OLLAMA_MODELO`.
